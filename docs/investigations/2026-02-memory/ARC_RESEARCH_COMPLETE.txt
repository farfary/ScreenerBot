KEY FINDINGS SUMMARY
════════════════════════════════════════════════════════════════════════════════

1. MEMORY LAYOUT
   ├─ ArcInner uses repr(C, align(2)) for pointer optimization
   ├─ Both atomic counters likely on same 64-byte cache line
   ├─ Layout properly handles inner value alignment with pad_to_align()
   └─ Overhead: 16 bytes per allocation (two 8-byte atomics)

2. FALSE SHARING
   ├─ Arc theoretically vulnerable but rarely problematic
   ├─ Strong modified frequently, weak infrequently
   ├─ Not typically contended by different threads simultaneously
   ├─ Use CachePadded<> only if profiling confirms cache misses
   └─ General-purpose type, not optimized for extreme contention

3. ATOMIC ORDERING
   ├─ Clone: Relaxed (1-3 cycles) - reference prevents deletion
   ├─ Drop: Release-Acquire (2-4 + 10-15 cycles on last ref)
   ├─ Weak.upgrade: Acquire CAS (2-8 cycles)
   ├─ make_mut: Acquire load (2-8 cycles or allocation cost)
   └─ Pattern borrowed from Boost ARC library

4. PERFORMANCE COSTS
   ├─ Clone operation: 1-3 cycles (very cheap)
   ├─ Drop (multi-ref): 2-4 cycles (cheap)
   ├─ Drop (last ref): 10-15 cycles (fence dominates)
   ├─ Typical 1M clones: 1-3 milliseconds
   └─ Contention multiplier: 1x to 10x+ depending on cores

5. ARCHITECTURE DIFFERENCES
   ├─ x86-64: Most expensive fences (MFENCE 10-15 cycles)
   ├─ ARM64: More efficient barriers (DMB ~5-10 cycles)
   ├─ RISC-V: Most flexible, implementation-dependent
   └─ Memory models differ significantly in weak ordering

6. SYNCHRONIZATION SAFETY
   ├─ Release-Acquire pattern ensures data visibility
   ├─ Drop's Release syncs with Upgrade's Acquire
   ├─ ThreadSanitizer compatibility via macro adaptation
   └─ Sound according to Rust memory model

BEST PRACTICES
════════════════════════════════════════════════════════════════════════════════

✅ DO:
  • Use Arc<T> by default for thread-shared data
  • Use Relaxed when reference existence prevents use-after-free
  • Use Release-Acquire for synchronization boundaries
  • Combine Arc with Mutex/RwLock for interior mutability
  • Use Arc::make_mut() for efficient copy-on-write
  • Profile before optimizing - overhead is usually minimal
  • Use CachePadded<> only after confirming cache issues
  • Read Boost ARC documentation for design rationale

❌ DON'T:
  • Use SeqCst unless you specifically need sequential consistency
  • Clone/drop Arc in tight loops without profiling
  • Assume ordering prevents false sharing (it doesn't)
  • Over-engineer early - Arc is well optimized
  • Pad/align structures prematurely
  • Mix Arc with complex lock hierarchies
  • Assume ordering differences matter uncontended
