KEY FINDINGS & INSIGHTS
================================================================================

1. MEMORY MODEL
   • Arc allocation: 16 bytes (counters) + 8 bytes (pointer) + data
   • Per-clone overhead: atomic increment operation
   • Per-drop overhead: atomic decrement + conditional deallocation
   • Cache-line aligned for efficiency

2. PERFORMANCE PROFILE
   • Clone: ~2-5x slower than Rc due to atomic operations
   • Deref: Free (simple pointer indirection)
   • High contention: Cache line bouncing in multi-threaded scenarios
   • Best for: Sharing immutable data or with Mutex for mutable

3. THREAD SAFETY GUARANTEES
   • Arc<T>: Send + Sync if T is Send + Sync
   • Arc alone protects only the reference count
   • Requires Mutex/RwLock for mutable shared data
   • Atomic operations enforce memory synchronization

4. CRITICAL OPERATIONS
   • Strong references: Prevent deallocation, must reach 0
   • Weak references: Don't prevent deallocation, allow cycles to break
   • Clone-on-write: Efficient mutation with Arc::make_mut()
   • Pinning: Guarantees data never moves via Pin<Arc<T>>

5. DESIGN TRADEOFFS
   • ✓ Thread-safe reference counting
   • ✓ Automatic memory management
   • ✓ Type-safe ownership semantics
   • ✗ Atomic operation overhead vs single-threaded
   • ✗ Possible reference cycles (must use Weak)
   • ✗ Lock contention in high-concurrency scenarios

================================================================================
PRACTICAL GUIDANCE
================================================================================

WHEN TO USE ARC:
├─ Sharing data across multiple threads ✓
├─ Shared read-only state ✓
├─ Shared mutable state (with Mutex) ✓
├─ Graph structures (with Weak for cycles) ✓
├─ Async task state sharing ✓
└─ When Rc has visible performance issues in multi-threaded code ✓

WHEN NOT TO USE ARC:
├─ Single-threaded code (use Rc instead) ✗
├─ Deeply nested Arc<Arc<T>> (unnecessary) ✗
├─ Arc<RefCell<T>> across threads (use Mutex) ✗
├─ When zero overhead is required ✗
└─ Simple stack allocation is sufficient ✗

OPTIMIZATION TECHNIQUES:
1. Minimize lock duration
2. Batch operations under single lock
3. Use RwLock for read-heavy workloads
4. Use Arc::make_mut() for clone-on-write
5. Profile before optimizing
