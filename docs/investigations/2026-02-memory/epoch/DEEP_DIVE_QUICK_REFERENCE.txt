KEY CONCEPTS AT A GLANCE
================================================================================

THE THREE-EPOCH INVARIANT:
┌─────────────────────────────────────────────────────┐
│ Epoch N-2: [PINNED] No threads, objects safe to free│
│ Epoch N-1: [OLD] Possibly active, cannot free      │
│ Epoch N:   [CURRENT] Being used, cannot free       │
└─────────────────────────────────────────────────────┘

THREAD PINNING:
let guard = epoch::pin();              // Declare epoch participation
let value = atomic.load(Acquire, &guard);  // Safe atomic access
// Operations deferred for this epoch
drop(guard);                           // Exit epoch, cleanup proceeds

DEFERRED CLEANUP:
guard.defer(move || {
    drop(expensive_resource);  // Executes when epoch is safe
});

DECISION QUICK-REFERENCE
================================================================================

USE EPOCH-BASED IF:
✓ Building lock-free concurrent data structures
✓ Need real-time latency guarantees
✓ Have high thread count (>4 threads)
✓ Building for Rust (type safety + epoch support)
✓ Memory overhead is a constraint

CONSIDER ALTERNATIVES IF:
✗ Simple reference counting (use Arc<T>)
✗ 95%+ reads (use RCU instead)
✗ General-purpose app (use GC languages)
✗ Single-threaded code (use Rc<T>)
✗ Dynamically spawning threads (use GC)

CODE EXAMPLE - BASIC USAGE
================================================================================

use crossbeam_epoch::{self, Atomic, Owned};
use std::sync::atomic::Ordering;

fn main() {
    // Create an atomic pointer
    let value = Atomic::new(42);

    // Reader: Pin the thread
    {
        let guard = epoch::pin();
        
        // Safe atomic load - protected by guard
        let read_val = value.load(Ordering::Acquire, &guard);
        println!("Read: {}", unsafe { *read_val });
        
        // guard auto-drops, cleanup deferred to safe epoch
    }

    // Writer: Compare-and-swap
    {
        let guard = epoch::pin();
        let new_val = Owned::new(100);
        let _ = value.compare_and_set(
            unsafe { read_val },
            new_val,
            Ordering::Release,
            &guard,
        );
    }
}

KEY POINTS:
1. Always pin before atomic access
2. Guard scope determines when cleanup can happen
3. No manual deallocation needed
4. Compiler enforces correct usage
5. Zero GC pause times

PITFALLS TO AVOID (6 Common Mistakes)
================================================================================

PITFALL 1: Forgetting to Pin
❌ let value = atomic.load(Ordering::Relaxed, ???);
✓ let guard = epoch::pin();
  let value = atomic.load(Ordering::Relaxed, &guard);

PITFALL 2: Holding Guard Too Long
❌ let guard = epoch::pin();
   expensive_io();          // Hold guard during slow operation
   network_call();
✓ expensive_io();
   network_call();
   let guard = epoch::pin();  // Pin only for critical section
   let data = atomic.load(...);

PITFALL 3: Unbounded Deferrals
❌ loop { guard.defer(...); }  // Indefinitely accumulates
✓ guard.defer(...);
   drop(guard);  // Ensure drop each iteration

PITFALL 4: Wrong Memory Ordering
❌ atomic.load(Ordering::Relaxed, &guard)  // Might see stale values
✓ atomic.load(Ordering::Acquire, &guard)  // Proper synchronization

PITFALL 5: Use-After-Free
❌ let guard = epoch::pin();
   let val = atomic.load(...);
   drop(guard);
   use_value(*val);  // ← val might be freed!

PITFALL 6: Incorrect Access Pattern
❌ let val = atomic.load(guard1);
   drop(guard1);
   use_value(val);  // ← guard1 is gone!
✓ {
     let guard = epoch::pin();
     let val = atomic.load(&guard);
     use_value(val);
   }  // Guard alive for entire use
